# Incident Response

機密情報や保護対象データが Git に入ってしまった、または外部から参照可能な状態になったときの対応手順です。  
**見た目の片付けより、まず封じ込め（被害拡大の停止）を最優先します。**

## 1. 封じ込め（Contain）

- 共有や外部同期を可能な範囲でただちに停止する
- **認証情報が含まれていた場合は即座に無効化・ローテーションする**（ファイルを消すだけでは不十分）
- 影響を受けた外部ストレージや公開先のアクセスを制限する

## 2. 影響の特定（Identify）

次の 5 点を記録します（**インシデント記録に漏洩した生値をコピーしないこと**）。

- 露出したデータの種別
- 第三者個人情報や勤務先・顧客情報が含まれるか
- リポジトリに入った時期
- リポジトリまたは派生物が外部から参照可能だったか
- アクセスした可能性がある人・システム

## 3. エスカレーション（Escalate）

- 勤務先・顧客・ベンダー・第三者の個人情報が含まれる場合は、単なる Git 作業で済ませず、適切なセキュリティ・プライバシー・法務窓口へ速やかに連絡する
- 法的・契約上の通知義務は事実関係と管轄によって異なるため、自己判断で隠さない

## 4. 除去（Eradicate）

- 現行ツリーから対象データを削除する
- 必要に応じて適切な履歴書き換えツールで Git 履歴から除去する
- 派生キャッシュ・インデックスを破棄して再構築する
- 添付ファイル・GitHub Actions アーティファクト・リリース・公開ミラー・Object Storage を個別に確認する

> 履歴書き換えは露出を減らしますが、すでに clone・fork・キャッシュされたコピーを回収することはできません。

## 5. 復旧（Recover）

- 認証情報のローテーション完了を確認する
- 無害化済みの正本データから派生インデックスを再構築する
- 機密情報スキャン（`python3 scripts/check_sensitive_data.py`）を実行する
- 漏洩内容を再現せずに原因を記録する

## 6. 再発防止（Learn）

```text
インシデント → 失敗モードの特定 → ガードレール追加 → テスト・自動化
```

実害が確認されなかったヒヤリハットであっても、そのまま流さず仕組みに落とし込みます。
