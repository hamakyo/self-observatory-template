# 記録前の安全チェック

隔離した原本から安全な保存候補を作り、本人確認の記録を付けたうえで Git へ移すためのローカル手順です。  
保存可否の基準は [DATA_POLICY.md](../DATA_POLICY.md) に従います。分類ツールは判断の補助であり、本人の確認を代行しません。


## 全体の流れ

```text
.quarantine/（原本を隔離）
  ↓ privacy-classify（リスク種別と修正案を確認）
_local/（原本を触らず、手動で最小化した候補を作成）
  ↓ privacy-approve（本人が確認してローカル承認を記録）
正本パスへコピー & git add
  ↓ privacy-check（ステージ済み内容と承認記録を照合）
commit / PR（通常の schema・機密チェックも実施）
```

## 1. 原本を隔離して分類する

1. 元のテキスト・PDF・DOCX・画像を `.quarantine/` に置きます（gitignore 対象）。
   - GitHub Issue や外部アプリへ原本を先に送らないでください。
2. ローカル分類ツールを実行します。

```sh
uv run self-observatory privacy-classify .quarantine/input.md
```

- 出力されるのは **情報種別・理由コード・一般的な修正案** だけです。
- 検出した生文字列・前後の文脈・ファイル名は出力されず、確信度は常に低く返ります。

## 2. 安全な保存候補を手で作る

原本は変更せず、再利用できる意味だけを抜き出した別ファイルを `_local/` に作成します。

- **第三者の再識別を防ぐ**：日付・場所・役割・組織の組み合わせを崩します。
- **業務情報を抽象化する**：職場の原文や構成図はそのまま持ち込まず、抽象化します。
- **認証情報は承認不可**：認証情報を含む原本は、この経路では承認できません。

## 3. 本人が確認して承認を記録する

原本と保存候補を本人が見比べ、保存先パスを決めたあとで承認コマンドを実行します。

```sh
uv run self-observatory privacy-approve .quarantine/input.md _local/candidate.md \
  --target memory/episodes/example.md \
  --source-class THIRD_PARTY_PERSONAL \
  --action anonymized \
  --owner-approved
```

### 主なオプション

| オプション | 指定できる値 | 補足 |
| --- | --- | --- |
| `--source-class` | `PUBLIC` / `SELF_PRIVATE` / `SELF_HIGH_SENSITIVITY` / `THIRD_PARTY_PERSONAL` / `EMPLOYER_CONFIDENTIAL` / `CREDENTIAL` | 本人の判断で選択。`PUBLIC` は公開元と保存権限を本人が確認する |
| `--action` | `minimized` / `anonymized` / `abstracted` | 候補に対して行った最小化・匿名化・抽象化の方法 |
| `--owner-approved` | フラグ | 本人確認済みであることを示す運用上の宣言（**AI が自律的に付けてはいけない**） |
| `--visual-reviewed` | フラグ | 原本または候補が PDF / DOCX / 画像の場合に必須（下記参照） |

高リスクの検出結果と `--source-class` が矛盾する場合や、候補に疑わしい箇所が残っている場合は承認せず保留します。

### PDF・DOCX・画像の目視確認（`--visual-reviewed`）

原本または保存候補に PDF・DOCX・画像が含まれる場合は、**本人が全ページ・全可視領域を目視確認した場合のみ** `--visual-reviewed` を付けます。

- Markdown へ書き換えた場合でも、原本の目視確認は省略できません。
- 原本を読み取れない場合は、候補が安全に見えても承認せず隔離に残します。
- PDF の画像・添付・注釈、DOCX の埋め込み・メタデータ、画像のメタデータや複数フレームも確認対象です。
- 候補側にこれらの検出が残る場合は保留し、安全な別形式や再作成した媒体に直してから再確認します。
- 機械検査は顔やスクリーンショットの内容を理解しません。

### ローカル承認記録に保存されるもの

承認記録は `_local/privacy/approvals.jsonl` に追記されます（ローカル専用、Git には入れません）。

- **記録する項目**：時刻、対象パス、原本と候補の SHA-256、Git に格納される候補・ポリシー・分類器の blob ID、本人が選んだ分類と修正方法、理由コード、承認記録 schema 版、実行した分類器の SHA-256
- **記録しない項目**：原文、一致文字列
- **失効条件**：ポリシーや分類器が更新されると旧記録は無効になり、再確認・再承認が必要です。

## 4. ステージ後に照合する（Git へ移す直前）

保存候補を指定パスへコピーして `git add` したあと、照合を実行します。

```sh
uv run self-observatory privacy-check
```

このコマンドは、変更された正本 Markdown と `assets/` の Git index 上の blob ID を、承認済みの保存先・候補 blob ID と突き合わせます。

- Git の改行変換や対象パスの clean filter は、承認時とステージ時で同じように適用されます。
- 内容が変わった、別パスへコピーした、現行ポリシー・分類器での承認がない場合は失敗します。
- 削除だけの変更には承認を求めません。
- 承認済みであっても、通常の schema 検証・機密情報スキャン・意味のレビューは必ず続けます。

## 制約と運用上の境界

- **CI では再検証できない**：承認記録はローカルにあるため、GitHub Actions では承認有無を確認できません。PR のマージ時に本人が差分と承認対象を照合します。
- **`--owner-approved` は本人認証ではない**：運用上の宣言であり、人間本人を技術的に認証する仕組みではありません。
- **Capture Issue は作成時点で GitHub に保存される**：ローカル CLI は外部コネクタによる Issue 作成を止められません。Issue を作る前に同じ分類・最小化を適用し、迷う場合は隔離領域に留めてください。
