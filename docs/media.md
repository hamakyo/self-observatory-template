# Media アーキテクチャ

> **特定のストレージではなく、「識別子と意味」を永続化する。**

画像や文書などのメディアは、**バイナリ実体** と **意味の記述** を 2 層に分けて管理します。

```text
assets/  → バイナリ実体（bytes）
media/   → 意味を表す Markdown（semantic memory）
```

バイナリを直接読めないエージェントやツールでも、`media/` の Markdown を通じて検索・参照できる設計です。

## セキュリティルール（必須）

**「証拠として便利だから」という理由で生のメディアを commit してはいけません。必ず無害化した派生版を保存します。**

テキストスキャナは画像の中身を読めないため、メディアには個別の確認ゲートが必要です。

- **画面・写真内の目視確認**：氏名・顔・アカウント ID・住所・顧客や勤務先情報・社内ツール UI・機密テキストがないか確認し、不要な識別子をトリミング／マスクする
- **メタデータ削除**：写真・画像から EXIF / GPS / 端末情報を削除する
- **図の再作成**：社内構成図などをそのまま貼らず、抽象化して描き直す
- **原本の隔離**：安全でない原本はローカル隔離または適切な別ストレージに置き、このリポジトリには入れない

ローカルの PDF・DOCX・画像候補を扱う場合は [記録前の安全チェック](privacy-ingress.md)（`--visual-reviewed` 必須）に従います。

## v0.1 の保存方針

| Git（`assets/`）に置いてよいもの（無害化済み） | 将来の Object Storage 候補（Git には置かない） |
| --- | --- |
| インスピレーション元の公開スクリーンショット | 大量の写真コレクション |
| 自作の図・生成したアーキテクチャ画像 | 動画・音声ファイル |
| 永続ノートに紐づく少数の無害化済み写真 | 高解像度の原本ファイル群・機械生成キャッシュ |

## ID とファイル命名規則

- **不変の stable ID**：すべての意味あるメディアに `media-personal-os-architecture` のような固定 ID を付けます。将来ストレージが変わっても ID は変わりません。
- **ファイル名**：重複検知しやすいよう、内容の短い SHA-256 プレフィックスを含めます（完全なハッシュは frontmatter に記載）。

```text
assets/images/YYYY/MM/<hash-prefix>-<slug>.webp
例: assets/images/2026/09/a81d39f2-personal-os-architecture.webp
```

## 将来の外部ストレージ移行

Git が肥大化した場合は、**バイナリ実体だけ** を Object Storage（Cloudflare R2 や S3 互換など。v0.1 の依存ではない）へ移し、正本の `media/` ノートと stable ID は Git に残します。

- 期限付きの署名 URL は永続参照として保存しません。
- 論理キーまたは stable media ID を実行時に解決する構造にします。

```text
stable media ID → resolver / metadata → 現在の物理ストレージ
```

## 想定する取り込みパイプライン

```text
生データ → ローカル隔離 → 機密・個人情報チェック → マスク・メタデータ削除
  → SHA-256 / 重複排除 → WebP 最適化（任意） → assets/
  → media/ Markdown 雛形生成 → 人間/AI で意味と関連を記述（レビュー必須）
```

> 画像からの視覚的推測はあくまで補助証拠であり、確定事実として無批判に扱いません。
